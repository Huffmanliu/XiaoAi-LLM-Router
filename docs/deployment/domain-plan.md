# 单域名部署与小米绑定分工：讨论稿

日期：2026-10-21，Asia/Shanghai。本文是建议，未修改DNS、证书、服务器代理或生产部署。示例中的`example.com`代表用户自己的域名，不是真实配置。

## 先分清三件事

- 域名：拥有`example.com`，通常可以在当前DNS服务中增加子域名，不必逐个再注册域名。
- 服务器：不同子域名可以指向同一台服务器、同一个公网IP；无需为网址分工先购买第二台服务器。DNS套餐和现有服务器能力仍需核验。
- 密码管理器：不同页面、不同来源和不同“站点”是不同概念。Chrome可能在同一主域名的子域之间匹配密码，子域不等于密码管理器的严格隔离。

来源：[Cloudflare创建子域记录](https://developers.cloudflare.com/dns/manage-dns-records/how-to/create-subdomain/)、[Google凭据共享说明](https://codelabs.developers.google.com/seamless-credential-sharing)。Google说明同站点网址（如www.example.com与m.example.com）可自动共享已保存凭据。

## 目前建议

先验证本次表单修正效果，再确定正式访问地址。暂不为密码弹窗购买第二个注册域名，也不把拆子域作为保证消除弹窗的方案。

本机表单已将小米密码的`new-password`改为`off`，登录区与不在使用中的业务页面移出当前文档，只有需要时才挂载；小米绑定提交前清空密码框，切离设备页也清空。保留密码遮挡、真实表单校验、键盘提交及绑定验证码流程。这些措施降低误判，不承诺控制Chrome或第三方密码扩展的原生提示。

[Chromium密码表单说明](https://www.chromium.org/developers/design-documents/form-styles-that-chromium-understands/)将`new-password`用于注册/改密；[Chromium安全FAQ](https://github.com/chromium/chromium/blob/main/docs/security/faq.md#why-does-the-password-manager-ignore-autocompleteoff-for-password-fields)明确密码管理器可忽略`autocomplete=off`。网站无法直接删除或修正用户密码管理器中已保存的错误条目。

## 一个域名的可选布局

| 地址示例 | 用途 | 当前是否必须 |
| --- | --- | --- |
| `example.com` | 原有网站或产品介绍，保留既有用途 | 不因本项目覆盖 |
| `speaker.example.com` | 用户登录、设备、历史；管理员按角色进入后台 | 正式上线先选定此类固定主入口 |
| `bind-speaker.example.com` | 专用小米绑定页 | 可选，需后端配套与浏览器验证后决定 |

不必为了管理员后台另设域名，当前角色权限仍由服务端验证。没有独立支付、下载等需求时，也不预设更多子域名。

分出绑定子域的价值是页面职责、来源检查和Cookie分工清楚；仍可能出现密码跨子域建议。如必须进一步隔离浏览器对两套密码的站点归属，再评估不同注册域名或经过验证的第三方授权方式。尚未确认现有小爱接口可直接改用官方扫码/OAuth，不把它当成现成功能。

## 以后实施会改哪些地方

1. **DNS**：为确定的主入口添加A记录指向服务器公网IPv4；只有服务器IPv6确实可用才加AAAA。可选绑定子域也可指向同一IP。保留已有根域、其他业务子域和MX等邮件记录，不把域名整体迁走。
2. **HTTPS入口**：使用现有Nginx或Caddy，按域名把请求转到内部服务。已有代理继续沿用，先检查80/443端口与其他网站，避免抢占。后端仍监听本机回环地址，浏览器只访问HTTPS。
3. **证书**：按选定主机名申请和自动续期即可，当前无需通配符证书。Caddy可自动管理HTTPS证书，须满足DNS和验证网络条件；若现有代理已有证书管理流程则沿用。[Caddy自动HTTPS文档](https://caddyserver.com/docs/automatic-https)
4. **后端域名限制**：现有平台只允许固定来源，不能仅增加DNS就声称绑定子域可用。若采用双子域，需要增加仅处理绑定的专用入口及严格的Host/Origin白名单，不开放通用跨域权限，也不把所有管理API映射到绑定域。
5. **Cookie**：平台登录Cookie只属于平台主机，不设置成覆盖整个`.example.com`。绑定页如需会话，使用独立、短时、只用于该次绑定的Cookie，不能拿到平台登录会话。生产启用Secure、HttpOnly和适合流程的SameSite策略。
6. **运行实例**：仍由原来的单个运行实例负责轮询和设备归属。网址变多不等于新增轮询进程，避免重复接管音箱。

## 若采用独立绑定页，用户会怎样操作

1. 在平台点“重新绑定当前小米账号”，平台先确认现有绑定是否真的失效。
2. 确需重验时，由平台生成短时、一次性的绑定凭证，绑定当前用户、会话、操作类型和当前小米身份。普通重新绑定不允许改账号；更换账号仍走独立确认流程。
3. 浏览器通过HTTPS POST进入绑定页。密码、验证码、平台登录令牌和绑定凭证不放在URL查询参数里；站点入口限制来源。绑定页完成该次凭证交换后不在刷新时重复消费凭证。
4. 用户输入小米密码，按需输入验证码。绑定页清楚标注本平台身份，不能让用户以为是小米官网。
5. 后端完成绑定并保存结果，返回预先确定的平台页面。平台用原登录会话读取本用户的结果，不相信浏览器自报“成功”，不接受任意返回网址。失败、取消或超时不覆盖原绑定。

上述跨站凭证、专用入口、Cookie及返回流程都尚未实施，不能把当前同源绑定页面直接搬过去就宣称安全隔离完成。

## 确定方案时需要的信息

域名名称、DNS服务商、根域及子域是否已有用途、生产服务器现有代理/证书管理方式。先做只读核验并给出具体DNS记录和代理变更，再由用户决定是否上线。域名规划不改变现有本机Play与生产触屏音箱的分工。
